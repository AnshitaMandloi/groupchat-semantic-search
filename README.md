# ChatMind — Semantic Search for Group Chats
🔗 **Live Demo:** https://groupchat-semantic-search-jy46usgf9q7cvchxthcdmq.streamlit.app
"When did we decide on Manali?" You remember the meaning, not the words. This
project builds search that understands meaning over a synthetic WhatsApp-style
group chat — semantic, attributed ("what did X say"), and temporal ("last
month") queries, all with full conversational context, not bare messages.

## What's inside

```
groupchat-search/
├── data/
│   ├── generate_corpus.py    # builds the synthetic 4,100+ message chat
│   ├── generate_queries.py   # builds the 41 ground-truth eval queries
│   ├── corpus.json           # generated chat (run generate_corpus.py to create)
│   ├── queries.json          # generated eval set
│   └── eval_results.json     # generated by evaluate.py
├── search/
│   ├── query_classifier.py   # detects semantic / attributed / temporal + filters
│   ├── engine.py             # hybrid BM25 + multilingual embedding search
│   └── evaluate.py           # runs the 41 queries, reports accuracy
├── app.py                    # Streamlit UI (search + eval dashboard)
└── requirements.txt
```

## How to run it (step by step — written for someone new to this stack)

You need Python 3.10+ installed. Everything else is one command.

**1. Open a terminal in the `groupchat-search` folder** and create a virtual
environment (keeps this project's packages separate from everything else on
your machine):

```bash
python3 -m venv venv
source venv/bin/activate        # on Windows: venv\Scripts\activate
```

**2. Install dependencies:**

```bash
pip install -r requirements.txt
```

This will take a couple of minutes the first time — `sentence-transformers`
pulls in PyTorch.

**3. Generate the corpus and eval set** (only needed once, or whenever you
want a fresh chat):

```bash
python data/generate_corpus.py
python data/generate_queries.py
```

You should see `Generated 4134 messages...` and `Total queries: 41`.

**4. Run the evaluation** (this is what proves the system works — needs
internet the first time, to download the embedding model):

```bash
cd search
python evaluate.py
cd ..
```

First run will download `paraphrase-multilingual-MiniLM-L12-v2` (~470MB,
one-time). You'll see a summary printed with top-1/top-5 accuracy broken down
by query type, and a list of any misses. This also writes
`data/eval_results.json`, which the UI's dashboard tab reads.

**5. Launch the UI:**

> Skip this step if you just want to try it — the live demo link at the top
> already runs this exact app.

```bash
streamlit run app.py
```

This opens a browser tab automatically (usually `http://localhost:8501`). If
it doesn't, click the URL it prints in the terminal.

## Design notes

**Why hybrid (BM25 + embeddings) instead of embeddings alone?** BM25 still
wins on exact terms, numbers, and names ("22-27 June", "Rajmachi") — vector
search can be surprisingly bad at exact-match recall. The fusion (weighted
reciprocal rank, 70% embedding / 30% BM25) lets each cover the other's blind
spot.

**Why a multilingual model specifically?** An English-only embedding model
treats "chalo Manali fix hai" as mostly out-of-vocabulary noise. Hinglish
needs a model trained across languages so "Manali fix hai" and "finalized the
destination" land near each other in vector space despite sharing zero
tokens and being different scripts/languages.

**Context expansion**: a single retrieved message is often meaningless
("theek hai" — okay to *what*?). Decision-thread messages are tagged at
generation time and expand to the full thread; everything else expands to a
fixed window of surrounding messages, since real reply-chains in chat exports
are sparse and don't reliably reconstruct a whole conversation.

## What embeddings get wrong (and how this mitigates it)

This is the part the assignment is actually testing for, so here's what I
found running the eval, not just what the theory predicts:

1. **Near-duplicate messages rank almost identically.** "kaunsa trek dekha
   hai" (which trek did you see) and "which trek did we finally pick" score
   nearly the same as the actual decision message, because they're
   semantically adjacent, not identical. This is why top-5 (not just top-1)
   and full-thread context matter — the right answer is very often *near*
   the top even when it's not first.

2. **Negation and stance are invisible to embeddings.** "did Priya agree to
   come on the trek" and Priya's actual reply "main nahi aa paungi" (I can't
   come) are semantically close — same topic, opposite polarity — because
   embeddings encode topic similarity, not logical polarity. The system has
   no dedicated fix for this; it's a known open problem with dense
   retrieval, and it's the most interesting failure mode in the eval set.

3. **BM25-only mode fails almost completely on the no-overlap subset by
   design** — in my own test runs without the embedding model loaded, top-1
   accuracy on the 23 zero-word-overlap queries was ~0%, while context-hit
   rate (answer present somewhere in the returned thread/window) stayed
   ~60%, purely from thread grouping getting lucky. That's the clearest
   demonstration in this whole project of why keyword search fails at
   exactly the moment you need it — and why the embedding step isn't
   optional.

4. **Sender attribution is a hard filter, not a ranking signal** — it's
   applied before scoring, so "what did Priya say" never accidentally
   surfaces someone else's message just because it scored higher. The
   trade-off: if the sender's message on that topic doesn't exist, the
   system won't gracefully fall back — it returns Priya's best-scoring
   message even if irrelevant, rather than admitting no match. Worth fixing
   with a relevance floor if this goes further.

## Known limitations / next steps

- Temporal parsing handles "last month", "this month", "in <month>", "last
  week", and ISO dates — not fuzzy ranges like "around when we booked the
  bus."
- Thread detection relies on explicit tags at generation time; on a real
  export you'd need a clustering step (time-proximity + topic similarity) to
  approximate this, since real reply-to metadata is sparse.
- No re-ranking with a cross-encoder — would likely help the ambiguous
  near-duplicate cases in point (1) above.
